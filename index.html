      Salt to Hash Demonstration

      Explore how cryptographically random salts transform deterministic password hashes, preventing rainbow table attacks and ensuring identical passwords generate unique stored digests.

      Why Salting Matters: A salt is a random string generated and concatenated with a password prior to hashing. Because the salt is unique for every credential, pre-computed rainbow tables cannot be used. Crucially: The salt is stored in plaintext alongside the password hash in the database—it does not need to be secret to protect against rainbow table attacks!

      Password Security Knowledge Base

      Comprehensive reference on cryptographic hashing, salting defenses, key derivation functions, and industry-standard password storage guidelines (OWASP, NIST SP 800-63B).

      // Core Cryptographic Distinctions
      Concept Direction Key Required? Primary Purpose Example
      Hashing One-way ($H(m) o h$) No key (Deterministic) Integrity check, password verification SHA-256, SHA-512
      Encryption Two-way ($E_k(m) leftrightarrow D_k(c)$) Yes (Secret key) Confidentiality of transmitted/stored data AES-256-GCM, RSA
      Encoding Two-way (Reversible) No key (Public scheme) Safe data transmission across text channels Base64, URL encoding
      // Fast Hashes vs Password Storage Functions
      ⚠️ Fast Hashes (DO NOT USE FOR PASSWORDS)

      Algorithms like MD5, SHA-1, and SHA-256 were engineered to compute digests on gigabytes of file data in milliseconds. Consequently, consumer GPU clusters can compute over 100 billion SHA-256 hashes per second. Storing raw or even salted SHA-256 passwords allows attackers to brute-force billions of combinations in seconds.

      🛡️ Slow KDFs (RECOMMENDED FOR STORAGE)

      Dedicated password-storage functions like Argon2id, bcrypt, scrypt, and PBKDF2 incorporate tunable computational work factors and memory-hardness. By forcing the computation to consume milliseconds of CPU time and megabytes of RAM, attackers are limited to a few thousand guesses per second.

      // Defenses: Salt vs Pepper
      🧂 Cryptographic Salt

      A unique, cryptographically random value (minimum 16 bytes) generated per user and stored in plaintext in the database next to the hash. Salts prevent pre-computed rainbow table attacks and ensure identical passwords produce distinct hash values.

      🌶️ Cryptographic Pepper

      A secret key stored separately from the database (e.g. in a hardware security module or environment secret). Even if an adversary dumps the database, they cannot hash candidate passwords without the pepper key.

      // Industry Password Storage Guidelines
      • Recommended Algorithm: Use Argon2id (winner of the Password Hashing Competition) with minimum $m=64\text{MB}$, $t=3$ iterations, and $p=4$ parallelism.
      • Fallback Algorithm: If Argon2id is unsupported by your environment, use bcrypt (work factor $\ge 12$) or scrypt.
      • Minimum Length: NIST SP 800-63B recommends allowing passwords up to 64 characters and setting a minimum of at least 8 characters.
      • Breach Blacklisting: Check new passwords against breach databases (e.g., Have I Been Pwned / top 100,000 weak passwords) rather than enforcing arbitrary periodic rotation.
